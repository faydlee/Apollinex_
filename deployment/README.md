# Подготовка Apollinex к развёртыванию

Этот файл фиксирует параметры приложения для будущего развёртывания. Сейчас проект готовится к запуску в закрытой лабораторной среде; это ещё не готовая конфигурация публичного многоузлового сервиса.

## Переменные окружения

`config/settings.py` читает переменные непосредственно из окружения процесса. Файл `production.env.example` служит только образцом: Django сам не загружает его и не читает `.env`.

Для PowerShell задайте настройки в том же окне, откуда запускаются команды или процесс приложения:

```powershell
$env:DJANGO_DEBUG = "false"
$env:DJANGO_SECRET_KEY = (& .venv\Scripts\python.exe -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())")
$env:DJANGO_ALLOWED_HOSTS = "apollinex.example.org"
$env:DJANGO_CSRF_TRUSTED_ORIGINS = "https://apollinex.example.org"
$env:DJANGO_SECURE_SSL_REDIRECT = "true"
$env:DJANGO_SECURE_HSTS_SECONDS = "0"
```

Сохраните секретный ключ в менеджере секретов целевой среды и используйте то же значение при последующих запусках. Не помещайте ключ, SQLite-базу или резервные копии в git или распространяемый архив.

Если TLS завершается на обратном прокси, включайте доверие к заголовку только при условии, что прокси удаляет входящий пользовательский `X-Forwarded-Proto`, задаёт его сам, а приложение недоступно в обход прокси:

```powershell
$env:DJANGO_TRUST_X_FORWARDED_PROTO = "true"
```

Пока HTTPS не проверен на конечном домене и поддоменах, оставьте HSTS равным `0`. После проверки HTTPS сначала используйте короткий срок, например `3600`, и только затем принимайте решение о годовом сроке, `includeSubDomains` и preload.

## Проверки перед запуском

Из корня репозитория, после настройки Python и переменных:

```powershell
.venv\Scripts\python.exe manage.py check --deploy
.venv\Scripts\python.exe manage.py showmigrations
.venv\Scripts\python.exe manage.py migrate --plan
.venv\Scripts\python.exe manage.py migrate
.venv\Scripts\python.exe manage.py createsuperuser
.venv\Scripts\python.exe manage.py collectstatic --noinput
```

Пока `DJANGO_SECURE_HSTS_SECONDS=0`, `check --deploy` ожидаемо предупредит об отключённом HSTS. Не включайте HSTS до проверки HTTPS на всех обслуживаемых именах. `collectstatic` создаёт `staticfiles/`; веб-сервер или выбранная платформа должны раздавать `/static/` из этой директории. Django `runserver` предназначен только для локальной разработки.

## Ограничения текущей конфигурации

- `requirements.txt` не содержит production WSGI-сервера и middleware для раздачи статики. Нужно выбрать целевую платформу/сервер и добавить только подходящие для неё компоненты.
- База остаётся SQLite. Используйте один экземпляр приложения на постоянном диске и согласованный процесс резервного копирования. Несколько экземпляров с общей SQLite-базой не поддерживаются этой конфигурацией.
- Когда `DJANGO_DEBUG=false`, `LoginRequiredMiddleware` требует входа через `/accounts/login/`; страницы входа и регистрации доступны гостям. История и страницы экспериментов показывают пользователю его записи и общие учебные примеры. Не назначенные владельцу старые записи доступны только в локальном режиме и суперпользователю для проверки/назначения.
- Перед миграциями резервируйте целевую базу и проверяйте копию. Не добавляйте рабочую базу, реальные таблицы измерений или секреты в пакет поставки.
- Отправка почты настроена на консоль; внешние уведомления не включены.

## Локальный запуск

Для локальной работы включайте отладочный режим только в текущем процессе:

```powershell
$env:DJANGO_DEBUG = "true"
.venv\Scripts\python.exe manage.py runserver
```

Локальная разработка использует SQLite в `db.sqlite3`. Не запускайте production-настройки через `runserver`.

## Явное назначение владельца старой работы

Команда назначает владельца только одной записи, если у неё ещё нет владельца и она не является общим демонстрационным примером. Сначала проверьте ID нужной работы и ID пользователя в базе, затем передайте оба ID явно:

```powershell
$experimentId = Read-Host "ID старого эксперимента"
$userId = Read-Host "ID пользователя"
.venv\Scripts\python.exe manage.py assign_experiment_owner $experimentId $userId
```

Проверьте ID, имя, пустое поле владельца и формат работы в административном списке перед запуском; используйте ID пользователя нужной учётной записи. Команда меняет только `Experiment.owner`; измерения, расчёты, исходные поля и дату изменения не затрагиваются. Повторное назначение, отсутствующая работа/учётная запись и общий демонстрационный пример завершаются ошибкой без изменений.
